# InkQuest 用户生成故事：云端技术方案

> 状态：实施方案草案  
> 范围：增量故事生成、可选 TTS、积分计费、登录与支付  
> 当前部署：Next.js 16 + OpenNext Cloudflare、Supabase Auth/Postgres、Lemon Squeezy  
> 原则：正式生成任务异步化；正文与 TTS 分项结算；用户身份只用 Supabase `user_id` 关联

## 1. 结论先行

推荐采用“轻 BFF + 异步队列 + 容器化生成 Worker”的架构：

```text
Browser
  │ Supabase session
  ▼
Next.js / OpenNext on Cloudflare
  ├── 登录态校验、参数校验、报价
  ├── 原子预留积分、创建 story/job
  ├── 查询故事与任务事件
  └── 创建 Lemon Squeezy Checkout
          │
          ▼
    Cloudflare Queue
          │ at-least-once
          ▼
Generation Worker（Node.js 容器，建议 Cloud Run 起步）
  ├── LLM：规划 / 场景 / 选项 / 释义消歧
  ├── story-pipeline：分词、拼音、词典、等级、校验
  ├── Tencent TTS / English TTS
  ├── 音频封装与词级时间轴
  └── 提交结果、结算或释放积分
          │
          ├── Supabase Postgres：故事、任务、积分、支付
          └── Supabase Storage：私有音频对象
```

不要把完整生成管线直接放入 Next.js Route Handler。当前 Web 应用运行在 Cloudflare Worker，而现有 pipeline 包含 `@node-rs/jieba` 原生二进制、`Buffer`、文件系统写入和长耗时外部调用，部署模型与 Worker 不匹配。Next Route Handler 适合作为公开 BFF，不适合作为长任务执行器。

## 2. 现状审查

### 2.1 可直接复用的部分

| 能力 | 现有位置 | 云端处理 |
| --- | --- | --- |
| 中英文富化分发 | `tools/story-pipeline/src/enrich/index.ts` | 抽为无文件系统依赖的 core |
| 中文分词 / 拼音 / 词典 / HSK | `tools/story-pipeline/src/enrich/zh.ts` | 保留在 Node 容器 |
| 英文分词 / 词典 / CEFR | `tools/story-pipeline/src/enrich/en.ts` | 保留并补全 IPA 数据 |
| TTS Provider 接口 | `tools/story-pipeline/src/tts/types.ts` | 作为云端供应商抽象 |
| 腾讯 TTS 签名与调用 | `tools/story-pipeline/src/tts/tencent*.ts` | 注入 Secret Manager 配置 |
| 字符片段转词级时间轴 | `tools/story-pipeline/src/tts/tencent.ts` | 增加对齐完整性校验 |
| 故事校验 | `tools/story-pipeline/src/validate.ts` | 改为节点级与故事级两层校验 |
| Supabase Auth | `src/lib/supabase/*` | 保留，补授权与用户初始化 |
| Lemon Squeezy Webhook 签名 | `src/app/api/webhooks/lemonsqueezy/route.ts` | 保留 raw body 验签，重写业务处理 |

### 2.2 当前不能直接搬云端的部分

1. `AUTHORING.md` 的 LLM 是本地 agent，不是线上 API；云端需新增 `LlmProvider`、结构化输出和 prompt 版本管理。
2. `assemble-story.ts` 通过 `readFileSync/writeFileSync` 读写仓库和 `public/audio`，线上需改成数据库与对象存储适配器。
3. 当前 schema 假设故事是一份完整静态 JSON；用户故事是逐节点增长，必须以关系表为事实来源。
4. `@node-rs/jieba` 是原生二进制，不应进入 Cloudflare Worker bundle。
5. 腾讯 TTS 的 MP3 使用 `Buffer.concat(audioParts)` 直接拼接；多段 MP3 可能出现重复头、时长识别或 seek 不稳定，应改为 PCM/WAV 拼接后统一编码，或使用 FFmpeg concat。
6. 当前英文 TTS 仍临时走腾讯兜底，正式上线前需确定英文供应商或明确质量降级策略。

### 2.3 登录与支付当前缺口

- Webhook 通过 `user_email` 更新 profile，邮箱不是稳定的支付关联主键。
- Webhook 没有保存 provider event id，重复投递可能重复发放权益或积分。
- Webhook 未检查数据库更新错误，也未持久化原始事件处理状态。
- 当前支付页面直接使用公开 Checkout URL，无法可靠写入不可伪造的 `user_id`、订单类型和积分包信息。
- `?success=` 查询参数直接控制成功 UI，不能证明支付已经完成。
- `profiles.is_premium` 只能表达布尔订阅，无法支持积分余额、预留、退款、赠送和到期。
- 登录 callback 的 `next` 需要限制为站内相对路径，避免开放重定向。
- 受保护写接口必须使用服务端 `getUser()` 校验，不以客户端状态或 `getSession()` 作为授权依据。

## 3. 服务边界

### 3.1 Next.js BFF（Cloudflare）

负责：

- 读取 Supabase session 并调用 `auth.getUser()`；
- 验证故事设定、选择、Director 指令与幂等键；
- 返回服务端报价；
- 调用 Postgres RPC 原子预留积分；
- 创建生成任务并投递队列；
- 返回任务状态、故事节点和签名音频 URL；
- 创建 Lemon Squeezy Checkout；
- 接收并验证支付 Webhook。

不负责：

- 直接调用长耗时 LLM；
- 运行 jieba 原生二进制；
- 在一次请求内完成正文 + 富化 + TTS；
- 把 service role key 或腾讯云密钥暴露给浏览器。

Next.js 16 Route Handler 默认不缓存写请求，适合作为公开 API；但所有 Route Handler 都是公开端点，必须在每个写入口执行认证、资源归属和额度检查。

### 3.2 Generation Worker（Node 容器）

建议初期使用 Cloud Run 部署一个 Node 20+ 容器，原因：

- 支持 `@node-rs/jieba` 原生依赖；
- 可包含 FFmpeg；
- 可加载本地只读词典文件；
- 适合长耗时、可重试任务；
- 可按并发与 TTS 限流配置实例。

它只接受内部签名请求或队列消费者转发，不向浏览器公开管理接口。

若未来希望全部留在 Cloudflare，需要先把 jieba 替换为 Workers 可运行的 WASM/纯 JS 实现，并验证长任务、音频封装和队列限制；不建议把这作为 MVP 前置。

### 3.3 队列

推荐 Cloudflare Queues：

- BFF 在数据库事务成功后投递 `generation_job_id`；
- Queue Consumer 使用服务凭据调用 Generation Worker；
- 消息按 at-least-once 处理，Worker 必须原子 claim 任务；
- 重试只复用同一 job，不再预留积分；
- 超过最大尝试次数后进入 dead-letter 流程并释放未结算积分。

为避免“数据库成功、队列投递失败”，使用 Transactional Outbox：事务内同时写 `generation_jobs` 和 `job_outbox`，定时 dispatcher 重投尚未确认的 outbox 记录。

## 4. Pipeline 云端重构

### 4.1 目标目录

```text
tools/story-pipeline/
  src/core/
    schema.ts
    enrich/
    timing.ts
    validate.ts
    pricing-input.ts
  src/providers/
    llm/types.ts
    llm/<provider>.ts
    tts/types.ts
    tts/tencent.ts
    tts/english.ts
    storage/types.ts
    storage/supabase.ts
  src/orchestrator/
    generate-opening.ts
    generate-scene.ts
    enrich-scene.ts
    synthesize-scene.ts
    commit-result.ts
  src/cli/
    ...保留现有本地入口
  src/worker/
    server.ts
    run-job.ts
```

CLI 和云端 Worker 调用同一个 core，区别只在 I/O adapter：

- CLI：本地 JSON + 本地文件；
- Worker：Postgres + Supabase Storage + 云端模型。

### 4.2 核心接口

```ts
interface LlmProvider {
  planStory(input: StoryPlanInput): Promise<StoryPlan>
  writeScene(input: SceneGenerationInput): Promise<SceneDraft>
  resolveGlosses(input: GlossResolutionInput): Promise<ResolvedGloss[]>
}

interface StoryRepository {
  loadState(storyId: string): Promise<StoryState>
  commitNode(input: CommitNodeInput): Promise<void>
  appendEvent(jobId: string, event: JobEvent): Promise<void>
}

interface AudioStorage {
  put(input: PutAudioInput): Promise<StoredAudio>
  createSignedUrl(objectKey: string, expiresInSeconds: number): Promise<string>
}
```

Provider 输入输出必须经过 runtime schema 校验。建议引入项目认可的 schema validator；不要只依赖 TypeScript 类型。

### 4.3 每个场景的执行顺序

```text
claim job
  → load story state + pricing version
  → safety check input
  → LLM write scene + 3 choices + branch seeds + state delta
  → safety check output
  → deterministic enrich
  → LLM resolve only ambiguous glosses
  → validate text segments / choices / state delta
  → transaction: commit text node + settle text credits
  → if TTS enabled:
       synthesize → package audio → validate timings → upload
       transaction: attach audio + settle TTS credits
  → release unused reservation
  → mark completed or partial_success
```

正文必须先于 TTS 独立提交。TTS 失败时任务状态为 `partial_success`，用户仍能阅读，并可创建只包含 `tts_scene` 的重试任务。

### 4.4 LLM 调用拆分

建议三类调用：

1. **故事规划**：只在开局或重大回溯时执行，输出人物、世界硬规则、开场冲突和隐藏走向。
2. **场景生成**：每次选择后执行，输出当前场景、三个选择、三个短分支种子和状态增量。
3. **释义消歧**：富化后批量处理需要释义的词，只返回候选索引或压简后的受约束释义。

不要一次预生成三个完整分支。未选择分支只保存 seed；选择后只生成一个完整场景。

每次调用记录：

- `prompt_version`；
- `model_provider/model_id`；
- 输入输出 token 或供应商 usage；
- latency；
- safety result；
- retry count；
- 关联的 job/node/version。

原始 prompt 和模型输出需要按隐私政策设置保留期，不能无限保存。

## 5. TTS 云端方案

### 5.1 产品语义

故事级字段：

```ts
type TtsPreference = {
  mode: "off" | "every_scene"
  voiceId: string | null
  speakingRate: number | null
}
```

MVP 只在 UI 展示“暂不需要 / 每段生成”。音色和语速保留数据库字段，但不在快速开局阶段展开。

### 5.2 任务与计费

一次场景生成包含两个可独立结算的 line item：

```text
scene_text   → 正文、选项、富化
scene_tts    → 音频、词级时间轴、存储
```

报价时预留两项；正文成功即结算 `scene_text`。TTS 成功才结算 `scene_tts`，失败则释放该部分。

### 5.3 音频封装修正

现有实现直接连接 MP3 Buffer，云端版改为：

1. 按供应商限制切分句子；
2. 优先请求 PCM/WAV；
3. 依据返回字幕计算每块时间轴偏移；
4. 拼接 PCM，并用 FFmpeg 一次编码为最终 MP3；
5. 校验总时长、时间戳单调性和 `timings.length === segments.length`；
6. 上传后再将 audio asset 标记为 ready。

若供应商只能返回 MP3，使用 FFmpeg concat，而不是裸 `Buffer.concat`。

### 5.4 缓存与版本

TTS 缓存键：

```text
sha256(normalized_text + lang + voice + rate + provider + provider_version)
```

对象路径建议：

```text
generated-audio/{user_id}/{story_id}/{node_id}/{node_version}/{content_hash}.mp3
```

任何正文版本变化都会生成新的 `content_hash`。旧对象延迟清理，避免回溯时间线仍引用它时被提前删除。

### 5.5 存储访问

- 使用 Supabase Storage 私有 bucket；
- 数据库只保存 bucket、object key、hash、duration 和 provider metadata；
- 客户端通过受保护 API 获取短时签名 URL；
- 不把长期公开 URL 写入故事节点；
- service role key 仅存在于 BFF 服务端与 Generation Worker。

## 7. 积分事务

### 7.1 服务端报价

客户端不提交可信价格，只提交动作和配置。服务端根据版本化规则返回：

```json
{
  "quote_id": "uuid",
  "pricing_version": "2026-08-a",
  "items": [
    { "type": "scene_text", "credits": "TBD" },
    { "type": "scene_tts", "credits": "TBD" }
  ],
  "total": "TBD",
  "expires_at": "..."
}
```

正式价格来自配置或 `pricing_rules` 表，本方案不写死数值。

### 7.2 原子预留

Postgres RPC `reserve_generation_credits(...)` 在一个事务内：

1. 锁定 `credit_accounts` 行；
2. 校验 quote、余额和幂等键；
3. `available -= total`，`reserved += total`；
4. 写 reservation 与 ledger；
5. 创建 story/job/outbox；
6. 返回已有或新建 job。

重复请求返回原 job，不重复扣费。

### 7.3 分项结算

- `settle_generation_item(reservation_id, "scene_text", actual)`；
- `settle_generation_item(reservation_id, "scene_tts", actual)`；
- `release_generation_item(...)`；
- 任务终态释放所有未使用金额。

预留过期任务由定时任务扫描，只有未被有效 lease 的 job 才可释放，避免长任务被误判。

## 8. 登录与授权完善

### 8.1 保留 Supabase Auth

现有 Magic Link + Google OAuth 足够 MVP。建议补齐：

- `auth.users` 创建后触发 `profiles` 与 `credit_accounts` 初始化；
- 新用户赠送积分通过 ledger `grant` 记录，额度由配置决定；
- callback 只允许 `next` 为站内 `/...` 路径；
- 所有生成写接口调用 `supabase.auth.getUser()`；
- DAL 提供 `requireUser()` 与 `requireStoryOwner(storyId)`；
- 生成入口未登录时保存草稿到 sessionStorage，登录返回后恢复；
- 按 user + IP + action 做速率限制，防止登录与生成接口滥用。

### 8.2 RLS

- 用户只能读取自己的 `generated_stories/nodes/jobs/events/audio_assets`；
- 用户不能直接写 credit、billing、job status；
- 用户可以通过受控 RPC 创建请求，不直接 insert 关键表；
- Webhook 与 Generation Worker 使用 service role，但所有写入仍携带明确 `user_id/story_id` 并记录审计；
- 公开分享故事另建 publish 状态和只读 view，不放宽私有表 RLS。

## 9. Lemon Squeezy 改造

### 9.1 Checkout 必须服务端创建

新增：

```text
POST /api/billing/checkout
  body: { product_code: "credit_pack_x" | "subscription_y" }
```

Route Handler：

1. `requireUser()`；
2. 由服务端 product catalog 将 `product_code` 映射到 Lemon Squeezy variant id；
3. 调 Lemon Squeezy API 创建 checkout；
4. 在 checkout custom data 写入 `supabase_user_id` 与 `product_code`；
5. 返回短时 checkout URL。

浏览器不传 variant id、价格、积分数量或 user id。

### 9.2 Webhook 处理

保留当前 raw body + HMAC 验签，之后：

1. 提取稳定 event id；
2. `INSERT billing_events ... ON CONFLICT DO NOTHING`；
3. 已处理事件直接返回 200；
4. 从 custom data 读取 Supabase user id；
5. 根据服务端 catalog 验证 variant 与权益；
6. upsert order/subscription/customer；
7. 若是积分包或周期额度，调用 credit grant RPC；
8. 标记 event processed；
9. 失败保存安全错误并返回可重试状态码。

不要再通过邮箱匹配 profile；邮箱只作收据与辅助排查。

### 9.3 支付成功页

`/billing/return?order_id=...` 只显示“正在确认”，随后查询服务端订单状态。只有数据库中的 webhook 结果为 paid/active 才展示成功和新余额。查询参数本身不构成成功证明。

### 9.4 产品模型

建议同时支持：

- **积分包**：一次性 grant；
- **订阅**：高级功能权限 + 每周期积分 grant；
- **Director Mode 权限**：由 entitlement 判断，不再只依赖 `profiles.is_premium`；
- **退款**：记录负 grant 或冻结尚未消费额度，规则需由业务确认；
- **额度是否滚存**：必须产品确认后写入 catalog，不在代码中猜测。

## 11. 前端任务状态

推荐状态机：

```text
queued
  → planning
  → writing_scene
  → enriching
  → checking_language
  → text_ready
  → preparing_choices
  → tts_generating（可选）
  → completed

异常：failed | partial_success | canceled
```

MVP 使用 `generation_job_events` + Supabase Realtime 推送阶段事件，断线后以 `GET job` 恢复。不要把每个 token delta 都写进 Postgres；正文可按完整段落提交，后续需要真正 token streaming 时再引入 Durable Object 或专用流服务。

## 12. 安全与合规

- 腾讯、LLM、Lemon Squeezy、Supabase service role 密钥进入各部署平台 Secret Manager；
- Worker 内部调用使用短时服务 JWT 或带 timestamp/nonce 的 HMAC，防重放；
- 用户输入做长度、枚举和 schema 校验；
- LLM 前后都执行内容安全检查；
- 对公开发布增加二次审核，不把“私有可生成”等同于“允许公开”；
- 日志不记录完整 session、密钥、支付 payload 中不必要的个人信息；
- Webhook 原始 payload 设置保留期与访问控制；
- 音频对象私有化，签名 URL 短时有效；
- 内部错误不直接返回模型或供应商原始信息。

## 13. 可观测性

每个请求贯穿：

```text
request_id → quote_id → reservation_id → job_id → story_id/node_id → provider_request_id
```

核心指标：

- 各 stage latency；
- 队列等待与重试次数；
- LLM/TTS 成功率与限流；
- TTS 对齐校验失败率；
- partial success 比例；
- 积分预留、结算、释放金额是否守恒；
- Webhook 延迟、重复事件和失败事件；
- 单场景真实供应商成本与积分收入映射。

报警优先级：余额不守恒、重复 grant、任务卡在 running、Webhook 持续失败、TTS/LLM 供应商限流。

## 17. 需要产品确认的决策

以下信息不应由工程实现自行猜测：

1. 每种动作的积分价格与版本更新规则；
2. TTS 是固定每段价格，还是按字符区间分档；
3. 订阅额度是否滚存、到期、退款后如何处理；
4. 免费用户可生成多少轮，Director Mode 的具体付费门槛；
5. 英文 TTS 供应商与音色质量标准；
6. 用户故事与模型输入输出的保存期限；
7. 私有故事是否允许成人内容、公开发布的审核标准；
8. Cloud Run 还是其他 Node 容器平台。

## 18. 最终建议

先做 Phase A + B，再接文字生成。积分账本和支付幂等不是生成系统上线后的“补丁”，而是生成任务的事务边界。TTS 应作为正文后的独立子任务：用户能更快开始阅读，音频失败不会拖垮故事，计费也能准确释放。

架构上继续保留 Cloudflare 负责 Web 和 BFF、Supabase 负责身份与事实数据、Lemon Squeezy 负责支付，把原生依赖和长任务放进 Node 容器。这样复用现有投资，同时避免为了“同一平台”强行重写已经验证过的 pipeline。
